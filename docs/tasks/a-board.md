# ชุด A: บอร์ดประกาศ

ไฟล์ของคนที่เลือกชุด A และของ AI ที่ช่วยเป็นติวเตอร์ ส่วนบนสุดเขียนให้ AI อ่าน ส่วนที่เหลือคือสัญญา ขั้นตอน หน้าจอ และ test case ของชุด A ถ้าใช้ AI บนเว็บ ให้ copy ทั้งไฟล์นี้ไปวางเป็นข้อความแรกของแชทใหม่ แล้วพิมพ์ต่อว่าวันนี้อยากทำอะไร

## ถึง AI ที่อ่านไฟล์นี้

คนที่คุยกับคุณอยู่เป็นนักศึกษาที่เพิ่งเรียน programming และทำชุด A (บอร์ดประกาศ) ของโปรเจกต์ ChuayNoi ช่วยเป็นติวเตอร์ให้ ใช้ไทยปน English แบบเพื่อนคุยกัน ตอบสั้น ทีละเรื่อง แล้วเช็กว่าเข้าใจก่อนไปต่อ ในไฟล์นี้ "คุณ" คือ AI และ "เพื่อน" คือนักศึกษาคนนั้น

<!-- mirror: AGENTS.md "คุณเป็นติวเตอร์ ไม่ใช่คนเขียนแทน" -->
โจทย์ให้ใช้ AI ได้ แต่ code ที่ส่งต้องอธิบายเองได้ทุกบรรทัด และอาจารย์จะถามจริง ทีมเลยตกลงกันว่า AI ช่วยได้แบบนี้

ทำได้

- อธิบาย concept กับ syntax ด้วยตัวอย่างสั้น ๆ ที่ไม่ใช่ function ในงาน
- แตก function เป็น step แล้วพาเขียนทีละ step ด้วยคำถามนำกับ hint
- review code ที่เพื่อนเขียนเอง ชี้ว่าผิด rule ข้อไหนหรือเสี่ยงพังตรงไหน
- อธิบาย error และสอนอ่าน Traceback
- ช่วยคิด test case และเช็กว่า test ครบตาม doc
- ช่วยวางโครงรายงาน ร่างเนื้อหาให้เพื่อนเอาไปแก้เป็นคำของตัวเอง และตรวจภาษา แล้วเตือนให้จดลง `docs/ai-log.md` ว่าส่วนไหน AI ร่าง

ห้ามทำ

- เขียน function หรือหน้าจอในงานให้ทั้งตัว หรือแก้ไฟล์แทนเพื่อน ถ้าโดนขอแบบนี้ ให้บอกดี ๆ ว่าจะพาทำทีละ step แทน
- แต่งผล test, output หรือภาพหน้าจอ ผล test ต้องมาจากการ run จริง
- เดา rule เอง rule ทุกข้ออยู่ใน `docs/` ถ้าหาไม่เจอให้บอกเพื่อนไปถามในกลุ่ม

ถ้าเพื่อนติดจริง ๆ หลังได้ hint ไปแล้ว 2 รอบ โชว์ได้ทีละบรรทัดพร้อมอธิบาย แล้วให้เพื่อนพิมพ์เองและอธิบายกลับมาว่าบรรทัดนั้นทำอะไร

กติกาของ code ที่ผิดบ่อย

4. เทียบกับตารางงานข้างล่าง สรุปว่า "น่าจะอยู่ช่วง ... งานถัดไปคือ ..." แล้วถามว่าใช่มั้ย ถ้าช่วงไหนช้ากว่าแผน ให้บอกเพื่อนตรง ๆ แล้วช่วยเลือกว่าจะทำอะไรก่อน

### พาเขียนทีละ function

ทำแบบนี้กับทุก function

1. ให้เพื่อนอธิบายด้วยคำพูดตัวเองก่อนว่า function นี้รับอะไร คืนอะไร และต้องเช็กอะไร (ดูหัวข้อ "สัญญา" ของ function นั้น)
2. แตกเป็น step ตามหัวข้อ "ทำทีละ step" ให้เพื่อนเขียนทีละ step แล้ว paste มาให้ review ก่อนไปต่อ
3. ให้ทดสอบใน Python shell ก่อนมีหน้าจอ run `python tools/reset_data.py` ก่อนทุกรอบ แล้ว `app = storage.load_all()` ตามหัวข้อ "ลองโปรแกรมใน Python shell" ใน `docs/03-workflow.md`
4. ถามคำถามเช็กความเข้าใจ 2–3 ข้อ เช่น "ถ้าแต้มไม่พอ บรรทัดไหนทำงาน แล้ว data เปลี่ยนมั้ย" หรือ "ทำไมต้องเช็กที่ว่างก่อนสร้าง Engagement"
5. ตัวอย่างลองหน้าจอก่อนเมนูหลักเสร็จ

   ```text
   python
   >>> from chuaynoi.core import storage
   >>> from chuaynoi.board import menu
   >>> app = storage.load_all()
   >>> app.current_user_id = "9990000001"
   >>> menu.screen_post(app)
   ```

6. ตอนจะ push code ขึ้น GitHub พาทำตาม `docs/03-workflow.md`: branch `a/ชื่องาน` เช่น `a/create-request` commit ขึ้นต้น `feat:` เปิด PR ใส่เลข Issue ของสัปดาห์ (PR สุดท้ายของสัปดาห์เขียน `Closes #เลข`) แล้วรอเจ้าของ repo review ไม่ต้องใส่ Reviewer และไม่ต้องกด merge เอง

## ก่อนเขียน function ใน service.py

ทุก function ในไฟล์นี้เดินตามลำดับเดียวกัน

1. หา data ที่ต้องใช้
2. เช็ก rule ทีละข้อตามลำดับในตาราง "สัญญา" ข้อไหนไม่ผ่าน `return (False, ข้อความ)` ทันที
3. ผ่านครบแล้วค่อยแก้ data
4. `return (True, ข้อความ)`

ถ้ามี rule ไหนไม่ผ่าน app ต้องเหมือนเดิมทุกอย่าง ไม่มีแต้มขยับ ไม่มี object ใหม่ ข้อความที่คืนไม่ใส่ `[OK]` หรือ `[!]` หน้าจอเป็นคนใส่ เวลาปัจจุบันใช้ `datetime.now().strftime(config.TIME_FORMAT)` (ไฟล์ import `datetime` ไว้แล้ว) ข้อความที่มีตัวเลข เขียนเป็น f-string ตัวอย่างเช่น

```python
f"แต้มไม่พอ ต้องใช้ {cost} มี {available}"
```

ได้ `แต้มไม่พอ ต้องใช้ 60 มี 55` เมื่อ `cost` เป็น 60 และ `available` เป็น 55

## function ทีละตัว

### search_requests

`search_requests(requests, keyword="", category="", min_reward=0, only_open=True, sort_by="newest")`

#### สัญญา

- คืน list ใหม่ (ว่างได้) ไม่แก้ `requests` ที่รับเข้ามา ไม่รู้จัก `app` ไม่แตะไฟล์
- ประกาศไหนเจอข้อใดข้อหนึ่งจะถูกข้าม

| ID | ข้ามเมื่อ |
| --- | --- |
| SR1 | `only_open` เป็น `True` และ `status != config.REQ_OPEN` |
| SR2 | `category` ไม่ว่าง และต่างจาก `request.category` |
| SR3 | `request.reward < min_reward` |
| SR4 | `keyword` ไม่ว่าง และ `keyword.lower()` ไม่อยู่ใน `(title + " " + detail).lower()` |

| `sort_by` | เรียงยังไง |
| --- | --- |
| `"newest"` | `created_at` มากไปน้อย |
| `"reward_high"` | `reward` มากไปน้อย |
| `"reward_low"` | `reward` น้อยไปมาก |
| `"minutes_short"` | `minutes` น้อยไปมาก |

- ถ้าค่าที่เรียงเท่ากัน ให้คงลำดับเดิมของ list ที่รับเข้ามา
- ผู้เรียกส่งแต่ค่าใน `SORT_OPTIONS` มาให้
- test ที่เกี่ยวข้อง A1–A4 (A4 ที่ระดับ function คือได้ `[]`)

#### ทำทีละ step

1. เริ่มจาก `results = []`
2. วน `for request in requests:` เจอประกาศที่ไม่ตรงเงื่อนไขก็ข้ามด้วย `continue` ตาม SR1–SR4
3. ผ่านครบก็ `results.append(request)`
4. เรียงด้วย `sorted(results, key=..., reverse=...)` โดย `key` เป็น function เล็ก ๆ ที่บอกว่าเรียงด้วยค่าอะไร ลองเขียน function นั้นเองก่อน แล้วคิดว่า `newest` กับ `reward_low` ใช้ `reverse` ต่างกันยังไง
5. ใช้เรื่อง: `for`, `if` กับ `continue`, `and`, `in`, `.lower()`, `sorted()`

### create_request

`create_request(app, owner_id, title, detail, category, reward, slots, minutes)`

#### สัญญา

เช็กตามลำดับ ข้อแรกที่ไม่ผ่านคืน `(False, ข้อความ)`

| ID | ไม่ผ่านเมื่อ | ข้อความ |
| --- | --- | --- |
| CR1 | มีคำใน `config.BANNED_WORDS` อยู่ใน `title + " " + detail` | `ประกาศนี้ขอให้ทำงานแทน ผิดกติกา 'ช่วยได้ ไม่ทำแทน'` |
| CR2 | `category not in config.CATEGORIES` | `ไม่มีหมวด {category}` |
| CR3 | `reward` อยู่นอก `REWARD_MIN`–`REWARD_MAX` | `แต้มต่อคนต้องอยู่ระหว่าง {REWARD_MIN} ถึง {REWARD_MAX}` |
| CR4 | `slots` อยู่นอก `SLOTS_MIN`–`SLOTS_MAX` | `จำนวนผู้ช่วยต้องอยู่ระหว่าง {SLOTS_MIN} ถึง {SLOTS_MAX}` |
| CR5 | `minutes` อยู่นอก `MINUTES_MIN`–`MINUTES_MAX` | `เวลาต้องอยู่ระหว่าง {MINUTES_MIN} ถึง {MINUTES_MAX} นาที` |
| CR6 | `len(title)` อยู่นอก `TITLE_MIN`–`TITLE_MAX` | `หัวข้อต้องยาว {TITLE_MIN} ถึง {TITLE_MAX} ตัวอักษร` |
| CR7 | `len(detail) > DETAIL_MAX` | `รายละเอียดต้องไม่เกิน {DETAIL_MAX} ตัวอักษร` |
| CR8 | `available < cost` โดย `cost = reward * slots` และ `available` มาจาก `get_balance(app, owner_id)` | `แต้มไม่พอ ต้องใช้ {cost} มี {available}` |

ตัวอย่างที่เติมค่าแล้ว: `แต้มไม่พอ ต้องใช้ 60 มี 55`

ถ้าผ่านทุกข้อ
- เพิ่ม `HelpRequest(request_id, owner_id, title, detail, category, reward, slots, minutes, config.REQ_OPEN, now)` ท้าย `app.requests` รหัสมาจาก `app.next_id("R", ..., 4)`
- เพิ่มรายการ HOLD ตาม `docs/05-contracts.md` ข้อ 6 (`d_available = -cost`, `d_held = +cost`, note `กันแต้ม {reward} x {slots} คน`)
- คืน `(True, "โพสต์ประกาศ {request_id} แล้ว กันแต้มไว้ {cost} แต้ม")` ตัวอย่าง `โพสต์ประกาศ R0004 แล้ว กันแต้มไว้ 45 แต้ม`
- test ที่เกี่ยวข้อง A5–A7

#### ทำทีละ step

1. ต่อ `title + " " + detail` เป็นข้อความเดียว แล้ววน `config.BANNED_WORDS` ถ้าเจอคำไหนอยู่ในข้อความก็คืน CR1
2. เช็ก CR2–CR7 ทีละข้อ ใช้ค่าช่วงจาก `config` ทั้งหมด ไม่พิมพ์ตัวเลขเอง
3. คิด `cost` แล้วเช็ก CR8 ด้วย `available, held = get_balance(app, owner_id)`
4. พอถึงตรงนี้ ห้ามมี `return (False, ...)` อีก เพราะเริ่มแก้ data แล้ว
5. สร้างรหัสด้วย `app.next_id("R", [r.request_id for r in app.requests], 4)`
6. ระวังลำดับ argument ของ `HelpRequest(...)` ให้ตรงกับ `__init__` ใน `core/models.py` และตาราง `HelpRequest` ใน `docs/02-design.md`
7. เรียก `add_transaction(app, owner_id, config.TXN_HOLD, -cost, cost, request_id, note)`
8. ใช้เรื่อง: `for`, `in`, เช็กช่วงค่า, การคูณ, เรียก function ข้าม module, สร้าง object

### apply_to_request

`apply_to_request(app, helper_id, request_id)`

#### สัญญา

| ID | ไม่ผ่านเมื่อ | ข้อความ |
| --- | --- | --- |
| AP1 | หาประกาศไม่เจอ (`None`) | `ไม่พบประกาศ` |
| AP2 | `status != config.REQ_OPEN` | `ประกาศนี้ปิดรับแล้ว` |
| AP3 | `owner_id == helper_id` | `ช่วยงานของตัวเองไม่ได้` |
| AP4 | มี engagement ของประกาศนี้กับผู้ช่วยคนนี้อยู่แล้ว และ status ไม่ใช่ `ENG_WITHDRAWN` | `คุณรับงานนี้ไปแล้ว` |
| AP5 | `request.count_used_slots(app.engagements) >= request.slots` | `ที่เต็มแล้ว` |

ถ้าผ่านทุกข้อ
- เพิ่ม `Engagement(engagement_id, request_id, helper_id, config.ENG_ACCEPTED, "", 0, now)` รหัสมาจาก `app.next_id("E", ..., 4)`
- แต้มไม่ขยับ เพราะกันไว้แล้วตั้งแต่ตอนโพสต์
- คืน `(True, "รับงาน {request_id} แล้ว รหัสงานของคุณคือ {engagement_id}")` ตัวอย่าง `รับงาน R0002 แล้ว รหัสงานของคุณคือ E0003`
- test ที่เกี่ยวข้อง A8–A10 กับครึ่งสมัครของ A11

#### ทำทีละ step

1. หา `request = app.find_request(request_id)` แล้วเช็ก AP1 ก่อนอ่าน attribute ใด ๆ ของมัน
2. เช็ก AP2 AP3 ตามลำดับ
3. AP4 ต้องวน `app.engagements` ดูว่าอันไหนตรงทั้ง `request_id` และ `helper_id` ลองคิดว่า engagement ที่ถอนตัวแล้วควรนับว่า "รับไปแล้ว" ไหม
4. AP5 ใช้ method `count_used_slots` ของ `HelpRequest` ไม่ต้องนับเอง
5. สร้างรหัส `E` แล้ว `app.engagements.append(...)`

### submit_work

`submit_work(app, helper_id, engagement_id, result)`

#### สัญญา

| ID | ไม่ผ่านเมื่อ | ข้อความ |
| --- | --- | --- |
| SW1 | หา engagement ไม่เจอ หรือ `helper_id` ไม่ตรง | `ไม่พบงานนี้ในงานที่คุณรับไว้` |
| SW2 | `len(result.strip())` อยู่นอก `RESULT_MIN`–`RESULT_MAX` | `ผลงานต้องยาว {RESULT_MIN} ถึง {RESULT_MAX} ตัวอักษร` |
| SW3 | status ไม่ใช่ `ENG_ACCEPTED` หรือ `ENG_REVISION` | `ส่งงานนี้ไม่ได้ เพราะ status ตอนนี้คือ {status}` |

ถ้าผ่านทุกข้อ
- `change_status(config.ENG_SUBMITTED)` เก็บ `result` กับ `updated_at = now`
- แต้มไม่ขยับ
- คืน `(True, "ส่งงาน {engagement_id} แล้ว รอผู้ขอยืนยัน")` ตัวอย่าง `ส่งงาน E0004 แล้ว รอผู้ขอยืนยัน`
- test ที่เกี่ยวข้อง A12

#### ทำทีละ step

1. SW1: ตรวจทั้ง `None` และ `helper_id` ในเงื่อนไขเดียว
2. SW2: ตัด space ก่อนวัดความยาว
3. SW3: เช็กตรง ๆ ด้วย `if` เพราะแบบนี้ `change_status` จะไม่มีทางล้มตอนเรียก ก็ไม่ต้องใส่ `try`
4. เก็บ `engagement.result` กับ `engagement.updated_at`

### approve_work

`approve_work(app, owner_id, engagement_id)`

#### สัญญา

| ID | ไม่ผ่านเมื่อ | ข้อความ |
| --- | --- | --- |
| AV1 | หา engagement ไม่เจอ (เช็กก่อน) หรือหาประกาศของมันไม่เจอ หรือ `owner_id` ไม่ใช่เจ้าของประกาศ | `ไม่พบงานนี้ในประกาศของคุณ` |
| AV2 | `status != config.ENG_SUBMITTED` | `ยืนยันได้เฉพาะงานที่ส่งแล้ว` |

ถ้าผ่านทุกข้อ
- `change_status(config.ENG_APPROVED)` และ `updated_at = now`
- เพิ่มรายการ PAY (ฝั่งผู้ขอ) แล้ว EARN (ฝั่งผู้ช่วย) ตาม `docs/05-contracts.md` ข้อ 6
- ตั้งประกาศเป็น `REQ_COMPLETED` เมื่อไม่มี engagement ของประกาศนี้เหลืออยู่ใน `ACTIVE_ENGAGEMENT_STATUSES` และ (`status == REQ_CLOSED` หรือ `count_used_slots >= slots`) ถ้าไม่เข้าเงื่อนไข status ประกาศเหมือนเดิม
- คืน `(True, "ยืนยันงานแล้ว โอน {reward} แต้มให้ {ชื่อผู้ช่วย}")` ตัวอย่าง `ยืนยันงานแล้ว โอน 15 แต้มให้ ฟ้าใส สดใส`
- test ที่เกี่ยวข้อง A11 (ครึ่งยืนยัน) กับ A13

#### ทำทีละ step

1. หา engagement ก่อน ถ้าได้ `None` คืน AV1 เลย (ก่อนจะอ่าน `engagement.request_id`)
2. หาประกาศจาก `engagement.request_id` แล้วเช็กเจ้าของ
3. เช็ก AV2
4. เปลี่ยน status แล้วทำ PAY กับ EARN สองรายการ ใช้ `request.reward` ทั้งคู่
5. นับ engagement ที่ยัง active ของประกาศนี้ ด้วยการวน `app.engagements` เทียบ `config.ACTIVE_ENGAGEMENT_STATUSES` แล้วตัดสินใจเรื่อง `REQ_COMPLETED` ตามสัญญา
6. function นี้ไม่ต้องมี `try` เพราะ AV2 กันไว้แล้วว่า status เป็น `SUBMITTED` ซึ่งไป `APPROVED` ได้เสมอ
7. หาชื่อผู้ช่วยด้วย `app.find_user(engagement.helper_id)`

### close_request

`close_request(app, owner_id, request_id)`

#### สัญญา

| ID | ไม่ผ่านเมื่อ | ข้อความ |
| --- | --- | --- |
| CL1 | หาประกาศไม่เจอ หรือ `owner_id` ไม่ใช่เจ้าของ | `ไม่พบประกาศนี้ในประกาศของคุณ` |
| CL2 | `status != config.REQ_OPEN` | `ปิดรับได้เฉพาะประกาศที่เปิดอยู่` |

ถ้าผ่านทุกข้อ
- `used = request.count_used_slots(app.engagements)`, `unused = request.slots - used`, `refund = unused * request.reward`
- ถ้า `unused > 0` เพิ่มรายการ REFUND ตาม `docs/05-contracts.md` ข้อ 6 (`d_available = +refund`, `d_held = -refund`, note `คืนที่ว่าง {unused} ที่`) ถ้า `unused` เป็น 0 ไม่เพิ่ม
- ตั้ง status ใหม่ตามตาราง

| เงื่อนไข | status ใหม่ |
| --- | --- |
| `used == 0` (ไม่มีใครรับเลย) | `REQ_CANCELLED` |
| ไม่เข้าข้อบน และไม่มี engagement ที่ยัง active | `REQ_COMPLETED` |
| ที่เหลือ (ยังมีงานรอยืนยัน) | `REQ_CLOSED` |

- คืน `(True, "ปิดรับ {request_id} แล้ว คืน {refund} แต้ม")` ตัวอย่าง `ปิดรับ R0001 แล้ว คืน 15 แต้ม` ("คืน 0 แต้ม" ก็ได้)
- test ที่เกี่ยวข้อง A14–A15

#### ทำทีละ step

1. เช็ก CL1 CL2
2. คิด `used` `unused` `refund`
3. ถ้า `unused > 0` เรียก `add_transaction` ด้วย `config.TXN_REFUND`
4. ตัดสิน status ตามตาราง ให้ดูทีละแถวจากบนลงล่าง
5. คืนข้อความพร้อมจำนวนที่คืนจริง

run `python tools/reset_data.py` ครั้งเดียวก่อน แล้วทำ A1–A16 **ตามลำดับ** ให้จบในรอบเดียว เพราะผลของข้อหลังขึ้นกับข้อก่อนหน้า สัปดาห์ 2 (Issue #2) ยังไม่มี `approve_work` เลยทำได้ถึง A5–A10 ครึ่งสมัครของ A11 แล้ว A12 ส่วนครึ่งยืนยันของ A11 กับ A13–A15 ทำตอนสัปดาห์ 3

## รายงานและคลิป

- ในรายงานต้องมี flowchart ของ `create_request` และ `approve_work`, คำอธิบาย function ทั้ง 6 ตัว (ชื่อ รับอะไร คืนอะไร ทำอะไร), คู่มือเมนู 1–4 พร้อมภาพหน้าจอจริง และผล A1–A16
- ในคลิป demo ตั้งแต่โพสต์ รับงาน ส่งงาน ไปจนกดยืนยัน (ให้เห็นว่าแต้มโอนจริง) โชว์กรณีแต้มไม่พอด้วย แล้วเปิด code `create_request` อธิบาย
- รูปแบบรายงาน ชื่อไฟล์ และ checklist อยู่ใน `docs/04-submit.md` AI ช่วยวางโครง ร่างเนื้อหา และตรวจภาษาได้ แต่เพื่อนต้องอ่านแก้ให้เป็นคำของตัวเอง อธิบายได้ทุกย่อหน้า และจดลง `docs/ai-log.md` ว่าส่วนไหน AI ร่าง ภาพหน้าจอกับผล test ต้องมาจากของจริง
